# 相册浏览优化验证（2026-11-11）

## 实现范围

- 相册列表按需生成独立 WebP 缩略图，长边按小、中、大三档限制为 512、768、1024 像素，保持原始比例，不放大小图片。
- 同时最多处理两个生成任务；相同照片对象、尺寸及文件元数据的请求合并。离屏时取消等待任务，已经开始的解码结束后丢弃失效结果并清理资源。
- 内存缓存限制为 150 个条目或 48 MiB Blob；正在显示的条目受到保护，可暂时超限，释放引用后再次清理。一个照片的不同尺寸占用不同条目。
- 列表不再写入原图 URL；预览、解析、分享和导出保留原图路径。共享图片组件默认继续使用原图，只有相册主动启用缩略图。
- 缓存按照片对象区分来源，并记录大小、修改时间；相册重新扫描后生成的新照片对象不复用旧对象的缓存。不主动监听磁盘文件变动。
- 列表分批结果缓存；日期分组选中状态复用；离屏占位考虑比例、边框、行列间距和移动端小图操作区，并合并尺寸变化后的计算。
- 不写入原始照片、IndexedDB 或备份目录。刷新页面后按需重新生成缩略图。

## 本地浏览器验证

见 `benchmark.json`。Windows 无头 Edge，开发服务器，1280×800 桌面视口；600 张 3840×2160 合成 JPEG，单日期分组；向下滚动 36 次，每次 650px、等待 250ms，再返回顶部。

对照组采用提交 `b596008` 的 PhotoGrid 和 WindowedPhotoBatch，使用当前公共样式和共享图片组件。属于组件级合成测试，不是完整旧版生产站点或用户真实相册的比较。

最终记录：

| 指标 | 对照组 | 优化后 |
| --- | ---: | ---: |
| 列表图片尺寸 | 3840×2160 | 768×432 |
| 挂载卡片峰值 | 180 | 180 |
| 滚动采样中的有效图片 URL 峰值 | 249 | 150 |
| 对应 Blob 总大小峰值 | 50,739,228 B | 1,802,400 B |
| 滚动结束时 photo.url 非空数量 | 276 | 0 |
| 长任务总时间（本次） | 1188ms | 484ms |
| 开始后等待 1.8 秒时已加载卡片 | 72 | 49 |

Blob 大小不代表浏览器解码、GPU 或总进程内存。测试使用相同图像内容的合成文件，实际图片复杂度和编码大小会不同。长任务受系统负载、开发构建和并行验证影响，不应据此给出固定加速比例。

缩略图首次生成有编码成本，首轮完成图片数量少于对照组；收益主要是减少列表长期持有的原图以及后续浏览的图片资源压力。没有宣称首次打开更快。

回归检查：

- 返回顶部：没有加载失败的卡片。
- 390×844、DPR 2：切换小图和竖图比例，生成 512×288 缩略图；保留选择状态，无加载失败。
- 切换为 100 个日期分组：100 个分组正常生成，当时只挂载 12 张卡片，无加载失败。
- 替换为 10 张照片：仅剩一个分组，保留 20 个缩略图 URL（同一照片的小、中两档）；没有加载失败或记录到的页面错误。
- 优化后整个组件卸载：有效缩略图 URL 为零。对照组件卸载未自行释放原图 URL；完整应用另有原图清理逻辑，所以该数字不能作为生产内存泄漏证据。
- 对照组记录到 ResizeObserver loop 通知；优化后本次未记录到页面错误。

## 自动化与构建

相关测试覆盖尺寸计算、编码失败清理、兼容解码、请求合并、并发与取消、LRU/容量限制、在用条目保护、照片替换和多尺寸清理、共享组件原图兼容、缩略图重试和卸载、布局高度变化、选择和收藏行为。

最终结果：6 个测试文件、20 项测试通过；类型检查、生产构建和本次涉及文件的格式检查通过。构建仍提示已有的混合导入和大包警告。

执行命令：

```powershell
npx vitest run tests/utils/photoThumbnail.test.ts tests/components/LazyPhotoImage.test.ts tests/components/WindowedPhotoBatch.test.ts tests/components/PhotoGridSelection.test.ts tests/components/PhotoFavorites.test.ts tests/utils/photoUrl.test.ts
npm run build
```

浏览器脚本：启动 `npx vite --host 127.0.0.1 --port 5198 --strictPort` 后执行 `node scripts/benchmark-album-performance.mjs`，需要本机 Edge 和本地基线提交。脚本会在组件目录创建临时对照文件，结束时删除，输出覆盖 `benchmark.json`。

## 尚未覆盖

没有使用用户的真实目录、移动设备、生产部署进行验收，也没有量化原图预览和导出的速度。原图路径通过代码检查确认未接入缩略图模块。低端设备上首次生成、快速滚动时的清晰度和缓存参数仍需要实际使用反馈。

当前采用三档尺寸，未动态跟随卡片逐像素宽度或屏幕 DPR，也没有在附近图片之间另外区分可见区优先级；主要通过限制预加载范围、取消过期任务和两路并发控制开销。持久化缩略图、Worker 编码及更精细的任务优先级留待真实数据验证后评估。
